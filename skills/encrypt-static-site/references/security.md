# Security model and runtime contract

## What is and is not protected

Only the generated deployment is intended for public hosting. Source, build output,
password files, local reports and Git history remain outside it. Making a source
repository public would expose that source even when its Pages artifact is encrypted.
Previously published plaintext must be treated as already disclosed.

The passive-download threat model is an attacker who obtains every public file
but not the passphrase. Filenames and file contents of the original site are inside
the encrypted payload. The generic shell, runtime, KDF parameters, site identifier,
base path, SPA setting and approximate bundle size are public. Visited route URLs
can appear in browser history or hosting logs. There is no traffic padding.

Offline guessing cannot be rate-limited by this architecture. Use a random strong
passphrase, not a memorable team name or a predictable sentence. Authorized users
can extract the files and all browser-visible credentials after unlock. This is
shared-secret confidentiality, not identity, per-user access control, DRM or audit
logging. Changing a password cannot erase downloaded/decrypted old versions.

HTTPS, host integrity and dependency integrity matter: an attacker who replaces
the unlock JavaScript can collect future passwords. No public password-unlock
application can authenticate its own delivery against a malicious host. This
implementation is an initial, tested release, not an independently audited product.

## Password entry through the agent

The default nontechnical workflow accepts the password in the skill invocation or
a follow-up chat message. That gives the agent permission to use it for encryption;
it does not make the conversation a secret-entry channel. Conversation history and
agent tool records may retain the password. Temporary-file cleanup cannot erase
those records. Use a unique site password, and never copy it into the public output,
project source, reports or completion message.

The agent supplies the password to the engine as stdin data, or uses a private
temporary file outside source and deployment and cleans it up afterward. It never
interpolates passwords into shell commands. The hidden terminal prompt is an
optional advanced workflow, not a requirement for users of the skill.

## Format version 1

- Package: UTF-8 JSON `{version: 1, files: [{path, type, data}]}`, with base64 file
  bytes. Paths are relative and preserved inside encryption. No ZIP extraction.
- Password key: Argon2id through pinned `hash-wasm`, 16-byte random salt, 64 MiB,
  3 iterations, parallelism 1, 32-byte result. No algorithm fallback.
- Site key: 32 random bytes generated by Node's cryptographic random generator.
- Payload and key wrapping: AES-256-GCM, independent random 12-byte nonces and
  128-bit authentication tags. Node and browser use Web Crypto's AES implementation.
- Both operations authenticate the same serialized metadata: version, random
  build ID, base path, SPA flag, KDF descriptor, salt and payload nonce. The wrapped
  key and payload must authenticate successfully before files become available.
- The browser enforces the exact supported KDF descriptor and checks envelope
  sizes. Public settings cannot force an arbitrarily expensive KDF invocation.
- The build verifies the complete decrypted package byte-for-byte and refuses
  extra or changed public files. A sampled plaintext scan adds a separate check.

The format separates the random site key from the password. Version 0.1 does
**not** implement in-place password rotation: rebuild to a fresh output with a new
password and random key, then replace the deployment. Old bundles remain susceptible
to their old password, even if removed from the current host.

## Browser lifetime and boundaries

The Service Worker holds a Map of decoded files. It uses no CacheStorage,
IndexedDB, localStorage or sessionStorage to persist keys or plaintext. Virtual
responses carry `Cache-Control: no-store`. This reduces intentional persistence;
it cannot guarantee erasure from browser internals, operating-system memory/swap,
extensions, password managers or an app that explicitly stores its own data.
JavaScript garbage collection cannot guarantee zeroization of every intermediate.

Unlocking is shared by all controlled tabs for the worker's scope in one browser
profile. It is **not per-tab authentication**. A separate browser profile must
unlock independently. Worker shutdown, updates or browser restarts lose the Map:
new navigations show the unlock shell; resource requests return 423 while locked.
An already open page can show old DOM or fail to load a lazy chunk until the user
reloads and unlocks. There is no guaranteed inactivity timer or offline mode.

Open `BASE + '_sealed/index.html'` to use **Lock all site tabs**. It clears the Map
and navigates currently controlled site tabs to the unlock screen. It cannot
revoke snapshots, downloads or browser-back copies. Closing one tab is not logout.

Use a dedicated origin controlled only by trusted code. URL subpaths are useful
for GitHub Pages routing but do not isolate mutually untrusted same-origin apps.
Existing PWAs/Service Workers conflict and must not be replaced silently. Avoid
concurrent unrelated apps in the scope. The engine reserves `sw.js` and `_sealed/`.

Virtual responses preserve binary bytes and MIME types, query-insensitive static
paths, extensionless HTML, directory indexes, single byte ranges and optional
document-only SPA fallback. Missing subresources return 404, never the HTML shell
after unlock. Non-GET/HEAD requests within the scope return 405. Cross-origin
requests remain normal browser networking and are not encrypted by this system.
Use a separate backend origin if the app needs runtime APIs.

Limits: 64 MiB total static bytes, 20,000 files, 96 MiB serialized package; the JSON
and base64 representation adds memory overhead. Argon2 also needs 64 MiB. Test real
mobile devices for substantial sites. This version is not for large media libraries,
streaming apps, PWA offline mode, cross-origin-isolated apps requiring custom
COOP/COEP behavior, or applications needing runtime server headers/redirects.

[Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API),
